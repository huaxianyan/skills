# 中文技术文案

写出像资深工程师写的中文：平实、具体、短句。

规则整理自阮一峰《中文技术文档的写作规范》，另加一份 AI 腔清单和两个扫描脚本。

## 硬规则速查

改文之前先记住这张表，它同时也是脚本的判据。

| 项 | 限值 |
| --- | --- |
| 逗号、顿号、冒号隔开的每一截 | 不超过 30 个汉字，尽量压到 20 以内 |
| 整句（按 `。！？` 切） | 不超过 100 个汉字 |
| 中文与英文、数字之间 | 加一个半角空格 |
| 中文句子的标点 | 全角 `，。：；？！（）` |
| 省略号 | `……`，不写 `...` 或 `。。。` |
| 破折号 `——` | 全文最多一两处，能改就改 |
| 分号 | 只用在并列分句之间。README 与发布说明建议不用 |
| 加粗 | 一屏最多一两处 |
| 段落 | 不超过 7 行，一段只说一个主题 |
| 中文里的感叹号、标题里的 emoji | 不用 |

引号风格随项目，见下面「引号与项目约定」。

## 句子

- 一句只说一个意思。长定语拆出去。
  - 差：那个昨天生病的人没有参加会议。
  - 好：他昨天生病了，没有参加会议。
- 用肯定句，不用双重否定。
  - 差：没有删除权限的用户，不能删除此文件。
  - 好：用户必须有删除权限，才能删除这个文件。
- 用主动语态，少用「被」。
  - 差：假如此软件尚未被安装。
  - 好：假如还没安装这个软件。
- 动词直接用，不套「进行」「做出」。
  - 差：对配置文件进行修改。
  - 好：修改配置文件。
- 「这」「其」「该」只指一个明确的对象。可能有歧义就把名词重复一遍。
- 名词前的修饰语不超过两层，多了就拆成两句。
- 分清「的、地、得」：开心的笑容、开心地笑、笑得开心。

## 语气

- 像给同事讲清楚一件事。可以口语化，不用网络流行语。
- 称呼读者用「你」，称呼项目方用「我们」。
- 用事实代替形容词。给出数字、命令、文件名、报错原文。
  - 差：性能得到了大幅提升。
  - 好：p99 延迟从 120 ms 降到 40 ms。
- 确定的事直接说。不确定就说清哪里不确定，以及怎么验证。

## 段落与结构

- 每段第一句是重点，后面的句子为它服务。
- 一段不超过 7 行。
- 标题不跳级，一级标题下面直接接二级。
- 同级标题只有一个时，去掉这一层。
- 下级标题不重复上级标题的名字。
- 需要四级标题时，改用 `**（1）小标题**` 或列表。
- 标题末尾不加句号、逗号、冒号。
- 列表只放真正并列、能单独扫读的条目。有因果或转折关系的内容写成段落。
- 加粗只给必须注意的警告或关键词。

## 排版

- 中文与英文、数字之间加一个半角空格：`在 Linux 上安装 5 个包`。
- 英文、数字后面紧跟全角标点时，中间不加空格：`他用的是 MacBook Air。`。
- 行内代码与中文之间**不加**空格：`` 用 `assembleRelease` 打包 ``。
- 并列的词用顿号隔开，最后一项用「和」连接：`Google、腾讯和百度`。
- 数字一律用半角。

数字（千分位、单位、范围、倍数）、括号、冒号、连接号、英文缩写的细则见 [references/typography.md](references/typography.md)。文中出现这些内容时读它。

## 引号与项目约定

默认用全角弯引号 `“ ”`，引号里再套一层用 `‘ ’`。

**有的项目约定用直角引号「」，此时以项目为准。** 本机各仓库里，syncclipboard、comeback-google-pinyin-input
等项目的约定就是直角引号，写这些项目时不要套用全角弯引号。开工前先看一眼项目的
`AGENTS.md`、`CLAUDE.md` 或已有的文档，确认引号风格再动手。

其余可以按项目覆盖的项，也一并写进项目的 `AGENTS.md`：分号是否禁用、某些词是否算业务术语
（例如「同步链路」「调用链路」在有些项目里是正式名称，不算 AI 腔）。

## AI 腔清单

自检时逐条对照。左边是要找的写法，右边是改法。

| 找这种写法 | 改成 |
| --- | --- |
| 开场套话：「随着……的发展」「在当今……」「值得注意的是」「让我们来看看」 | 删掉，第一句直接说内容 |
| 结尾套话：「总的来说」「综上所述」「总而言之」，或重复前文的总结段 | 删掉。确实需要结尾就只写新信息，比如下一步做什么 |
| 客套话：「希望对你有帮助」「如有问题欢迎交流」 | 删掉 |
| 对比句式：「不是 A，而是 B」「与其说 A，不如说 B」 | 直接说 B |
| 递进句式：「不仅……而且/更……」 | 拆成两个陈述句 |
| 硬凑三个：三连排比形容词、每组都是三项的列表 | 有几项写几项 |
| 设问自答：「关键是什么？答案很简单：」 | 直接给结论 |
| 宣传腔形容词：「强大、灵活、无缝、全面、极致、优雅、轻松、一站式」 | 换成具体事实，没有事实就删 |
| 黑话：「赋能、抓手、闭环、链路、沉淀、对齐、颗粒度、维度、底层逻辑、范式、打通」 | 换成白话。代码或业务里的正式名称保留 |
| 破折号插入解释 | 改用逗号、冒号、括号，或拆成两句 |
| 翻译腔：「进行 + 动词」「通过……的方式」「作为一个……」、一句里多个「的」 | 直接用动词，拆开长定语 |
| 过度含糊：「在某种程度上」「在一定情况下可能会」 | 确定就直接说。不确定就说清条件 |
| 感叹号、emoji 标题或列表符号 | 句号，纯文字标题 |
| 每段都加粗、一两句话也拆成列表、小标题比段落还密 | 按「段落与结构」重排 |

## 扫描脚本

两个脚本都只报告，不改文件。装在本项目的 `scripts/` 下，直接用 Python 3 跑，不依赖第三方包。

```bash
python scripts/check_style.py <文件或目录>...      # 标点、空格、AI 腔词、破折号、分号、长句
python scripts/check_clauses.py <文件或目录>...    # 句长（整句 100 字 / 分截 30 字）
```

脚本自带几条降噪规则：引号与行内代码里的内容不参与判定，`- 差：` 开头的反例行跳过，
表格行不参与句长统计，代码文件只看注释行。要是某个词仍然被报出来，说明它在正文里是裸写的，
那就是真问题。

`check_style.py` 的输出分两档：

- 前三列是 `文件:行号 [类别]`，普通类别是问题，`存疑:xxx` 要人工判断，可能是业务术语。
- 末尾的 `统计` 行给出每个文件的行尾、引号数、破折号数、分号数。

常用参数：`--ext md,kt,py` 指定扫描的扩展名（默认含常见文本与代码后缀），`--only-issues` 只看问题，
`--quiet` 只输出没有问题的结论。

扫描结果里的两类提示要留意：

- `分号(该文件禁用)` 只在 README 和 release-notes 目录下出现，其余文件里的分号可能是正常用法。
- 长句提示是启发式的。口语化的长句可以留，但连着几条就说明该拆了。

## 流程

**写新文档**

1. 先想清楚读者是谁，读完要能做成什么事。一句话说不清就先问用户。
2. 按上面的规则写。
3. 过一遍 AI 腔清单。
4. 跑两个脚本，逐条处理。
5. 引号、省略号、破折号这三项脚本判断不完整，人工再看一眼。

**改已有文档**

1. 通读全文再动手。
2. 用户只要意见时，按「原句 → 改后 → 原因」列出问题，不改文件。
3. 否则直接改，然后做上面的第 3 到 5 步。

改完的说明只用两三句，讲清改了哪几类问题、共多少处、涉及多少文件。

## 批量改文的做法

一次改十几个文件时，不要逐条调用编辑工具。用「显式补丁列表」的脚本：每个补丁写清
`(文件, 原文, 新文)`，先全量校验每条命中且仅命中 1 次，全部通过后再落盘。

这样做的两个好处：命中数不对会立即报错，不会静默改错位置。一次执行就能校验全部补丁。

两个坑要记住：

- **行尾不统一。** 同一仓库里有的文件是 LF，有的是 CRLF。写补丁脚本要用
  `io.open(path, newline="")` 读，然后按 `"\r\n" if "\r\n" in text else "\n"` 换算模式里的 `\n`。
  用默认的 universal newline 读会把 CRLF 归一成 LF，导致 `"\r\n" in text` 永远为假。
- **不要把长中文塞进 `python -c "..."`。** shell 会吃掉反引号，内容会静默丢失。写成脚本文件再执行，
  并在写完后断言关键片段确实在文件里。
