# 项目开发规范与交接

在一个项目里干活，先把四件事立好规矩：

- 凭据不出会话，私钥只让工具直接使用。
- 项目约定只有一处，写在项目的 `AGENTS.md` 里。
- 进度有记录，下一个执行者能自己接上。
- 每件事开工前有预期时长，超了就停下来报告。

## 凭据与私钥

### 私钥只能被直接使用

允许的做法：让 SSH 客户端、Git、`scp`、`rsync -e ssh`、`ssh-agent` 拿着私钥去连接和传输。密钥材料全程留在文件里，由工具自己读。

不允许的做法：读取、解密、复制、打印、比对、备份私钥内容。`cat`、`head`、`xxd`、`strings`、`openssl rsa`、`ssh-keygen -y` 读私钥都在禁止之列，哪怕只是想确认格式。这类命令一旦执行，密钥材料就进入了会话记录，等同泄露。

确认私钥能不能用，用连接本身验证，不要去看密钥：

```bash
ssh -o BatchMode=yes -o ConnectTimeout=5 <host> true
```

确认连接走的是哪把钥匙、哪个代理，只看配置与远端：

```bash
grep -nE '^(Host|HostName|IdentityFile|ProxyJump|ProxyCommand)' ~/.ssh/config
git remote -v
```

私钥口令由用户本人输入。不代填、不写进脚本、不放进环境变量文件，也不让 `ssh` 之外的工具接触它。

### 其他凭据同理

API token、证书私钥、keystore 口令、数据库密码、云厂商密钥都属于同一类东西。要引用它们时走既有通道：环境变量、`.env`、`git credential.helper`、`gh auth`、系统 keyring。命令里不出现明文，日志里不出现明文。

### 读文件前先确认

读服务器或仓库里的配置文件之前，先看文件名、大小和目录，判断它是否可能装凭据。确认过再读全文。

有一条真实教训值得记住：为了确认 TLS 复用形态，直接 `cat` 了含 DNS API token 的配置，token 进入会话记录，最后只能轮换。代价和收益完全不成比例，而那次想确认的信息，`grep` 一两行就能拿到。

### 已经泄露时

- 立即告知用户，说明读了什么文件、为什么会读到、后果是什么，并建议轮换。
- 不在回复里复述凭据明文，也不把明文写进任何文档或提交。
- 记录事故时写清机制和影响，不抄凭据本身。

### 提交前自查

```bash
git diff --cached | grep -nE 'BEGIN [A-Z ]*PRIVATE KEY|ghp_|github_pat_|xox[baprs]-|AKIA[0-9A-Z]{16}'
```

命中就停下来处理，不要先提交再想办法。

## 项目约定文件（AGENTS.md）

### 分层

约定按作用范围分三层，项目级只写项目特有的东西：

- **机器级**：这台机器的工具、路径、代理、JDK、SDK 等，所有项目共用。
- **开发根目录级**：某一批项目的共同要求，例如回答语言、图片读取授权。
- **项目级**：只对当前仓库成立的事实与规则。

上层已有的内容不要在项目级重复一遍。重复之后，两边改动不同步，读者也不知道该信哪一份。

### 项目级该写什么

- 回答语言与风格要求。
- 必须遵守的流程：分支策略、验收方式、合入与清理、发布顺序。
- 构建、测试、发布的命令与关键路径，以及不能违反的工具约束。
- 环境与工具的实际位置和版本约束。
- 写入边界：哪些目录可以自由写，哪些操作必须先取得授权。
- 凭据与外部访问：凭据放在哪、用哪个通道引用，只写位置不写内容。
- 术语表与命名约定，包括哪些词在本项目里是正式名称。
- 可复现的已知坑，写清现象、原因和绕法。
- 决策记录：谁在什么时候定下什么，替代了哪条旧约定。

### 项目级不该写什么

- 密钥、令牌、口令，任何形式都不写。
- 进度流水、每日动态、本轮结论，这些属于进度文档。
- 一次性命令、临时故障、未经验证的推测。
- 上层已经写过的通用规则。
- 从别处抄来的、和本项目无关的规范。

### 维护方式

- 写之前先验证事实，别把推测写进去。
- 新决定要显式写明替代了哪条旧约定，避免两套说法并存。
- 旧条目失效时就地修订，不保留新旧两份说明。
- 每轮任务确认了新的稳定事实后就更新，不攒到最后一次写。

### 本地文件边界

项目的 `AGENTS.md` 通常只服务本地开发，不加入 Git、不推送、不进发布产物。接管仓库时用仓库本地的 `.git/info/exclude` 忽略它。发现它已被跟踪，就保留本地文件并从仓库中移除索引。

需要团队共享的工程约束另写公开文档，不能让本地约定文件成为唯一来源。

## 开发进度文档（交接记忆）

### 作用是交接，不是日记

进度文档存在的唯一理由，是让下一个执行者不用重读整个仓库和整段会话，就能接着干。写的时候只想一件事：对方看完能不能直接动手。

### 选形态

两种形态都可以，按项目规模选一种并固定下来：

- **单一时间线**：`docs/STATUS.md`，一条一条追加，适合长期项目。条目多了以后按编号或日期检索。
- **决策文件加日期流水**：`MEMORY.md` 记长期决策，按日期分文件记当轮流水，适合工作目录已被忽略的项目。

无论哪种，都要有一个能被 `grep` 命中的固定开头，例如日期加序号。

### 一条记录写什么

- 日期与本轮目标。
- 改动的仓库、分支与提交 SHA，部署则写清镜像或版本号。
- 验证方式和结果：跑了什么命令、观察到什么现象、多少条样本。
- 结论与其边界：哪些是实测，哪些是推断，哪些没覆盖。
- 未完成项与下一步。
- 被推翻的旧结论要指名作废，并给出反证依据。

### 不写什么

- 对话寒暄、过程性试错的长日志、被放弃方案的完整细节。
- 没有核实的推测当成结论写。
- 能通过 `git log` 查到的东西原样抄一遍，只留 SHA 与一句话说明。

### 更新时机

任务收尾、分支合入、部署完成、实验得出否证结论、发现旧记录有误时，都当场更新。

### 交接时怎么读

1. 先读最新几条记录和长期决策文件，建立当前主线。
2. 现场核对状态，不凭记录相信：`git status`、当前分支、`git log -1`、CI 结果。
3. 找未完成项和阻塞，确认它们是否仍然成立。
4. 确认凭据、设备、外部服务的可用状态，再开始动手。
5. 发现记录与实际不符时，先查清哪边是新的，再修订记录。

记录里的 SHA 和状态是当时的快照。读的时候要核对当前值，不能直接沿用。

## 任务预期与超时

### 先给出预期，再动手

跑任何可能超过十几秒的命令前，先说清三件事：这步要做什么、大概多久、超时就怎么办。没有预期就没有「卡住」这个判断，只能一直等下去。

```text
预期：全量测试约 3 分钟，给 6 分钟超时；超过就改跑单模块并报告。
```

### 命令必须带超时

- 秒级命令直接跑。
- 分钟级命令显式设超时，不留无限等待。用工具的超时参数，或让命令自己带限制：

```bash
timeout 600 ./gradlew test
curl -sS --max-time 30 -o out.bin "$url"
```

- 安装依赖、下载、网络请求、连远程设备这几类必须设超时。它们卡住时通常不会自己报错。
- 不要用后台进程加轮询来绕开超时。那样等待时间只是换了个地方，问题没解决。

### 超时后的动作

第一次超时的正确反应是缩小范围，不是原样重跑：

1. 确认进程真的结束了，别留下孤儿进程占着端口或锁。
2. 先跑最小可用单元：单条用例、单个模块、单次请求。能过说明是规模问题，不能过说明是环境或代码问题。
3. 把输出写进文件再分段读：`./gradlew test > /tmp/test.log 2>&1`，然后只看尾部与失败行。超长输出直接回传会淹没会话。
4. 第二次仍然超时，就停下来报告，不试第三次。

### 停下来的报告格式

```text
卡在哪：<命令与当前状态>
已确认：<这一步排除掉什么>
需要：<用户要做的决定或提供的条件>
建议：<下一步的最小验证>
```

一句话说「还在跑」不算进展，也不算汇报。

### 长任务分批推进

- 分批执行，每批报一次进度：扫 200 个文件分四批，每批 50 个。
- 大范围扫描、批量改文、大仓库克隆这类工作，先估算规模再决定批次。
- 批量操作先做一份全量校验，再落盘，不要一边跑一边改。

### 什么时候必须停下来问

- 任务规模明显超出预期，例如「先扫一下」实际是十几个 GB。
- 需要跨越授权边界，例如写项目目录外的位置、改动服务器。
- 同一件事连续两次失败，原因还不明确。
- 用户取消过一次的操作，不要在没说明原因的情况下重试同一形态。

## 交接清单

给下一个执行者的最小信息集，可以直接复制去填：

```markdown
## 当前状态

- 仓库与分支：<仓库> / <分支>
- 提交：<SHA>，工作区<干净 / 有改动>
- CI 与部署：<结果与版本>
- 设备与环境：<设备、代理、外部服务是否可用>

## 本轮完成

- <改了什么，验证到什么程度>

## 未完成与阻塞

- <事项>：<卡在哪，需要什么才能继续>

## 下一步建议

1. <动作> → <验收方式>
```

## 接手新项目时的适配清单

- 约定文件在哪，是否已从 Git 索引移除。
- 进度文档在哪，用哪种形态，最新一条是什么时候。
- 凭据放在哪，用哪个通道引用。
- 构建、测试、发布的命令，以及版本号的唯一来源。
- 外部访问的授权范围，哪些操作必须再确认。
- 回答语言与文案规范，引号风格尤其要先看一眼。
- 哪些命令是分钟级甚至小时级的，各自的可接受时长是多少。
